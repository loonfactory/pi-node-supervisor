## 1. 개요

### 1.1 배경

Raspberry Pi를 이용한 키오스크, 카메라, 센서 및 배치 처리 장치는 실제 작업이 없는 시간에도 계속 켜져 있는 경우가 많다. 단순한 예약 종료는 운영체제를 끌 수 있지만, 꺼진 운영체제만으로 다음 부팅을 예약할 수 없으므로 수동 조작이나 별도 전원 제어 장치가 필요하다.

Raspberry Pi 5는 내장 RTC(Real-Time Clock)와 wake alarm을 제공하며, 주 전원이 연결된 상태에서 보드를 저전력 대기 상태로 전환한 후 RTC 알람으로 다시 부팅할 수 있다. 그러나 이를 실제 운영에 사용하려면 부트로더 설정, 시간대 변환, RTC 알람 검증, 안전 종료, 일정 복구 및 장애 진단을 일관되게 처리하는 프로그램이 필요하다.

### 1.2 목적

본 문서는 Raspberry Pi 5의 내장 RTC를 이용해 장치의 종료와 기동을 자동 관리하는 `pi-power-manager`의 개발 목적, 제품 구성, 범위 및 추진 방향을 정의한다.

본 문서는 제품 수준의 방향을 확정한다. 상세 기능·인터페이스·품질 요구사항은 SRS-PIPOWERMANAGER-001에서, 내부 모듈 구조·API·상태 모델·권한 분리는 후속 설계서에서 정의한다. 본 문서에 기술되지 않은 사항은 미확정으로 간주한다.

### 1.3 용어

- **RTC:** 운영체제와 독립적으로 시각을 유지하고 알람을 제공하는 Raspberry Pi 5 내장 시계다.
- **wake alarm:** RTC에 기록하는 미래의 절대 시각으로, 저전력 대기 상태의 Pi 5를 다시 부팅하는 데 사용한다.
- **관리형 종료:** `pi-power-manager`가 다음 기동 가능성을 검증한 뒤 수행하는 정상 종료다.
- **저전력 대기:** 외부 주 전원은 연결된 채 Pi 5의 주요 전원 출력을 끄고 RTC 알람을 기다리는 상태다. 외부 전원 공급 자체를 차단하는 것을 뜻하지 않는다.
- **일정:** 종료 및 다음 기동 시각을 결정하는 일회성 또는 반복 규칙이다.
- **보류:** 일정 정의를 삭제하지 않고 자동 종료 실행만 일시적으로 막는 상태다.
- **검증:** 설정한 wake alarm을 다시 읽어 요청한 미래 시각과 일치하는지 확인하는 절차다.

## 2. 구성

### 2.1 프로젝트 목적

`pi-power-manager`는 다음 구성 요소로 이루어진 headless 전원 일정 관리 프로그램으로 개발한다.

| 구성 요소 | 역할 |
|---|---|
| Scheduler | 일회성·반복 일정과 시간대를 해석해 다음 종료·기동 시각을 계산 |
| RTC Adapter | Pi 5의 RTC 및 wake alarm 읽기·기록·삭제·검증 |
| Power Coordinator | 사전 조건과 종료 훅을 확인하고 안전한 시스템 종료를 조정 |
| Service | systemd 환경에서 일정을 감시하고 재시작 후 상태를 복구 |
| CLI | 일정 관리, 보류·재개, 상태 조회, 진단 및 시험 기능 제공 |

일정 계산과 정책은 하드웨어 접근에서 분리하며, Raspberry Pi 5 의존 동작은 RTC 및 전원 어댑터 경계에 한정한다. 상세 구조와 인터페이스는 설계서에서 정의한다.

### 2.2 기본 동작

시스템의 기본 동작은 다음 순서를 따른다.

1. 기동 시 하드웨어, RTC, 시스템 시각, 부트로더 설정 및 저장된 일정을 점검한다.
2. 현재 시각과 활성 일정에서 다음 종료 및 기동 시각을 계산한다.
3. 종료 시각이 되면 종료 사전 훅을 실행한다.
4. 다음 기동 시각을 RTC wake alarm에 기록하고 다시 읽어 검증한다.
5. 모든 필수 조건이 성공한 경우에만 정상 종료를 요청한다.
6. Pi 5는 저전력 대기 상태에서 RTC 알람을 기다린 뒤 다시 부팅한다.
7. 서비스는 저장된 일정과 이전 실행 상태를 읽고 다음 동작을 재계산한다.

## 3. 개발 범위

### 3.1 포함 범위

- Raspberry Pi 5 내장 RTC 및 wake alarm 제어
- 일회성, 매일 및 요일별 종료·기동 일정
- IANA 시간대 기반 일정과 UTC 절대 시각 변환
- RTC 알람 기록, read-back 검증 및 과거 알람 정리
- 종료 전 사용자 정의 훅과 제한 시간
- RTC 또는 설정 오류 시 종료를 취소하는 실패 안전 정책
- 일정 보류·재개 및 관리형 종료 취소
- systemd 기반 자동 실행과 재부팅 후 상태 복구
- 일정 관리·상태 조회·진단·dry-run을 위한 CLI
- 설정 및 런타임 상태의 영속화
- journald 기반 동작 결과와 실패 원인 기록

### 3.2 제외 범위

- Raspberry Pi 4 이하, Raspberry Pi 500 및 Compute Module 지원
- 외장 RTC, UPS, 스마트 플러그 및 전원 제어 HAT 지원
- USB-C 전원 공급 자체의 물리적 차단·인가
- 그래픽 데스크톱, 웹 UI 및 모바일 앱
- 여러 Raspberry Pi의 중앙 집중식 관리
- 소비 전력 측정, 요금 계산 및 최적화 추천
- 원격 운영체제·펌웨어 업데이트
- 타 프로그램이 소유한 RTC 알람의 강제 덮어쓰기
- 주 전원이 끊긴 상태에서의 예약 부팅 보장

### 3.3 초기 개발 범위

초기 개발은 Raspberry Pi 5와 Raspberry Pi OS 64-bit headless 환경에서 단일 장치의 일정을 관리하는 CLI·systemd 서비스로 한정한다. 일회성 일정과 안전한 RTC 종료·기동 주기를 먼저 검증하고, 이후 매일·요일별 반복 일정, 보류·복구 및 운영 진단 기능을 추가한다.

초기 버전은 외부 전원이 계속 연결되어 있다는 전제를 가진다. RTC 백업 배터리는 주 전원 상실 시 시각 보존을 위해 권장하지만, 주 전원이 없는 동안 보드를 기동시키는 수단으로 취급하지 않는다.

## 4. 추진 방향

### 4.1 기술 방향

| 항목 | 방향 |
|---|---|
| 대상 플랫폼 | Raspberry Pi 5, Raspberry Pi OS 64-bit |
| RTC 인터페이스 | Linux RTC sysfs `/sys/class/rtc/rtc0/wakealarm` |
| 개발 언어 | Python 3 우선 |
| 배포·실행 | systemd 서비스와 CLI, 단일 장치 구성 |
| 설정·상태 | 사람이 검토 가능한 선언형 설정과 원자적 런타임 상태 저장 |
| 로그 | journald, 프로그램적으로 식별 가능한 이벤트 |
| 검증 | 단위·통합 테스트와 Raspberry Pi 5 실기기 시험 |

지원할 Raspberry Pi OS와 Python의 정확한 최소 버전은 Phase 0에서 고정한다.

### 4.2 전원 관리 방침

다시 켜질 수 있을 때만 끈다. 시스템은 유효한 다음 기동 시각을 계산하고 RTC에 기록한 값의 read-back 검증이 성공한 경우에만 관리형 종료를 수행한다. 다음 기동 시각이 없거나 RTC 검증이 실패하면 종료하지 않는다.

시간 기준을 분리한다. 사용자는 지역 시간과 IANA 시간대로 반복 일정을 정의하며, 내부 계산·영속화·RTC 기록은 모호하지 않은 절대 시각을 사용한다. DST 경계의 처리 정책은 SRS와 설계서에서 명시하고 시험한다.

오류는 가동 보존으로 수렴한다. 일정 충돌, 설정 오류, RTC 접근 실패, 시계 불일치 또는 종료 훅 실패가 발생하면 기본적으로 장치를 켜 둔 채 오류를 보고한다. 자동 종료 성공보다 복구 가능성을 우선한다.

RTC 알람 소유권을 존중한다. 기존 알람이 본 시스템이 설정한 것인지 확인할 수 없으면 자동으로 덮어쓰지 않는다. 공존 및 소유권 판정 방식은 설계서에서 정의한다.

변경은 원자적으로 적용한다. 일정과 상태 변경은 검증 및 영속화가 성공한 뒤 적용하며, 실패 시 기존 정상 상태로 계속 동작한다.

권한을 분리한다. RTC 쓰기와 시스템 종료에 필요한 코드만 높은 권한으로 실행하며, 상태 조회와 일정 계산은 가능한 한 일반 권한에서 수행한다.

### 4.4 주요 위험 및 대응 방침

부트로더 설정 오류. 저전력 종료 설정이 올바르지 않으면 RTC 알람 기동이 실패할 수 있으므로, 자동 종료 활성화 전에 필수 설정을 진단하고 실기기 시험을 요구한다.

RTC 알람 충돌. 다른 프로그램이 wake alarm을 사용하면 일정이 덮어써질 수 있으므로, 기존 값과 소유 상태를 확인하고 충돌 시 종료를 중단한다.

시간대 및 DST 오류. 지역 시각이 존재하지 않거나 두 번 존재할 수 있으므로, 반복 일정에는 IANA 시간대를 저장하고 경계 정책을 자동화 시험으로 고정한다.

시계 불일치. 시스템 시각과 RTC 시각이 크게 다르면 과거 또는 잘못된 알람을 설정할 수 있으므로, 허용 오차를 넘으면 관리형 종료를 중단한다.

상태 손상. 전원 손실 중 설정 파일이 손상될 수 있으므로 원자적 저장과 마지막 정상 상태 복구를 사용하며, 복구할 수 없으면 자동 종료를 비활성화한다.

권한 범위 확대. RTC와 종료 제어 때문에 전체 프로그램이 root로 동작할 위험이 있으므로, 권한 경계를 설계하고 입력·훅 실행을 제한한다.

제품 범위 오해. 저전력 대기와 물리적 전원 차단이 혼동될 수 있으므로, 외부 전원 연결 전제를 설치 및 운영 문서에 반복해 명시한다.

## 5. 확정 사항 및 검토 과제

### 5.1 확정 사항

- 공식 지원 하드웨어는 Raspberry Pi 5로 한정한다.
- Raspberry Pi 5의 내장 RTC와 wake alarm을 사용한다.
- 외부 주 전원은 저전력 대기 중에도 연결되어 있어야 한다.
- 제품은 headless systemd 서비스와 CLI 형태로 제공한다.
- 초기 일정 유형은 일회성, 매일 및 요일별 반복으로 한다.
- 유효한 RTC 알람을 기록하고 검증하지 못하면 관리형 자동 종료를 수행하지 않는다.
- 오류 및 모호한 상태에서는 장치의 가동을 보존한다.
- 외부 전원 차단 장치, 웹 UI 및 중앙 관리는 초기 범위에 포함하지 않는다.
- 요구사항은 SRS-PIPOWERMANAGER-001에서 영역별 ID와 검증 방법으로 관리한다.

### 5.2 검토 과제

- 지원할 Raspberry Pi OS, 커널 및 Python의 최소 버전 확정 → Phase 0
- 일정 표현을 종료·기동 시각 쌍과 가동 구간 중 무엇으로 제공할지 → SRS/설계서
- 누락된 종료·기동 일정의 처리 정책 → SRS/설계서
- DST 중복·누락 시각의 선택 정책 → SRS/설계서
- RTC 알람 소유권 식별 및 다른 프로그램과의 공존 방식 → 설계서
- 종료 훅 기본 제한 시간과 강제 종료 허용 여부 → SRS
- 설정 파일 형식과 CLI 변경의 영속화 경계 → 설계서
- 최소 권한 프로세스·IPC 구조 → 설계서

- 웹 UI 및 다중 장치 관리의 후속 범위 편입 여부 → 초기 출시 후 검토
