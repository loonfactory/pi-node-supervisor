## 1. 개요

### 1.1 배경

하나의 Raspberry Pi 장치에서 CaptureNode, 센서 수집기, 원격 유지보수 서비스와
`pi-power-manager`를 함께 운영하려면 각 프로그램의 일정과 전원 상태를 일관되게
조정해야 한다. 사용자가 촬영 시각, 센서 수집 시각 및 유지보수 가능 시간만
정의하더라도 실제 실행에는 서비스 준비 시간, 작업 완료 대기, 일정 병합, RTC 기동
시각 및 안전 종료 시각 계산이 필요하다.

각 프로그램을 개별 설정하면 촬영 중 종료, 다음 기동 누락, 불필요한 전원 주기,
서로 다른 시간대 해석 및 데이터 확인 경로 분산이 발생할 수 있다. 또한 장치 내부에
새로운 수집 노드가 추가될수록 사용자가 각 프로그램의 세부 구동 방식을 직접 관리하기
어렵다.

### 1.2 목적

`pi-node-supervisor`는 사용자가 장치에서 수행할 업무와 시각만 선언하면 이를
검증된 실행 계획과 전원 계획으로 변환하고, 장치 내부의 로컬 노드를 조정하는
Supervisor다. Web UI를 통해 업무 일정을 작성하고 자동 생성된 전원 계획, 노드 상태,
각 노드가 생성한 데이터 및 실행 이력을 통합 조회할 수 있게 한다.

Supervisor는 촬영, 센서 수집, RTC 및 종료 기능을 직접 재구현하지 않는다. 각 기능은
CaptureNode, 센서 노드 및 `pi-power-manager`가 소유하고, Supervisor는 명시적인
어댑터 계약을 통해 설정, 실행 준비, 상태 및 데이터 조회를 조정한다.

### 1.3 용어

- **장치:** `pi-node-supervisor`와 관리 대상 프로그램들이 함께 실행되는 단일
  Raspberry Pi다.
- **로컬 노드:** 같은 장치 안에서 독립적인 기능과 데이터 소유권을 가진 관리 대상
  프로그램이다. CaptureNode, 센서 수집 노드 등이 해당한다.
- **업무 일정:** 사용자가 정의하는 촬영, 센서 수집, 유지보수와 같은 목적 중심의
  일정이다.
- **실행 계획:** 업무 일정에서 계산한 서비스 준비, 작업 실행, 완료 대기 및 정리
  타임라인이다.
- **전원 계획:** 실행 계획을 만족하기 위해 계산한 `power-on`과 `power-down` 가동
  구간이다.
- **파생 계획:** 사용자가 직접 편집하지 않고 업무 일정과 정책으로부터 Supervisor가
  생성하는 실행 계획 및 전원 계획이다.
- **노드 데이터:** 로컬 노드가 생성하거나 소유하는 이미지, 센서 측정값, 결과 파일,
  상태 및 이벤트다.
- **데이터 카탈로그:** Supervisor가 노드 데이터를 통합 조회하기 위해 관리하는
  메타데이터와 위치 정보다.
- **revision:** 검증을 통과해 적용된 통합 설정과 파생 계획의 불변 버전이다.

### 1.4 관련 프로젝트

| 프로젝트 | 역할 | 소유권 경계 |
|---|---|---|
| CaptureNode | 카메라 촬영과 촬영 결과 저장 | 촬영 실행 및 이미지 원본 소유 |
| pi-power-manager | RTC wake alarm 검증과 안전 종료 | RTC 접근 및 실제 종료 요청 소유 |
| pi-node-supervisor | 업무 일정, 파생 계획과 로컬 노드 조정 | 통합 의도, 적용 revision 및 조회 경험 소유 |

## 2. 제품 원칙

### 2.1 사용자는 업무만 정의한다

사용자는 다음과 같은 의도를 정의한다.

- 특정 시각 또는 구간의 촬영
- 특정 시각 또는 주기의 센서 수집
- 원격 유지보수를 위해 장치를 켜 두는 시간
- 작업별 프로필과 선택 매개변수

서비스 시작 시각, 부팅 여유 시간, 작업 종료 대기, 전원 구간 병합, RTC 알람 및 종료
시각은 Supervisor가 정책에 따라 계산한다.

### 2.2 파생 계획을 설명 가능하게 만든다

자동 생성된 전원 계획에는 각 구간을 만든 업무 일정, 적용한 준비·정리 시간, 병합
이유 및 다음 RTC 기동 시각을 함께 제공한다. 사용자는 적용 전에 원래 업무 일정과
파생 계획을 비교할 수 있어야 한다.

### 2.3 오류는 가동 보존으로 수렴한다

필수 노드가 준비되지 않았거나, 작업 완료를 확인할 수 없거나, 다음 기동 시각과 RTC
검증이 불확실하면 장치를 종료하지 않는다. 자동 종료보다 데이터 완결성과 복구
가능성을 우선한다.

### 2.4 데이터 소유권을 유지한다

이미지와 센서 원본은 생성한 로컬 노드가 소유한다. Supervisor는 원본을 임의로
이동하거나 변환하지 않고, 어댑터를 통해 메타데이터를 색인하고 조회한다. 원본 삭제와
보존 정책은 노드별 계약과 사용자 권한을 따른다.

### 2.5 오프라인 로컬 동작을 기본으로 한다

Supervisor, Web UI 및 로컬 노드는 인터넷이나 중앙 관제 없이 한 장치 안에서
동작한다. 장치가 꺼져 있는 동안 Web UI에 접속할 수 없으므로 원격 접속이 필요한
시간은 유지보수 업무 일정으로 등록해야 한다.

## 3. 사용자 경험

### 3.1 대시보드

대시보드는 다음 정보를 한 화면에서 제공한다.

- 시스템 시각, 시간대, RTC 시각과 동기화 상태
- 현재 실행 중인 업무와 관련 로컬 노드
- 다음 업무, 다음 `power-down` 및 다음 RTC `power-on`
- 현재 적용 revision과 Draft 변경 존재 여부
- 로컬 노드별 건강 상태와 마지막 성공·실패
- 최근 생성 데이터 요약과 저장 공간 상태
- 자동 종료 준비 상태 및 직접적인 차단 원인

### 3.2 업무 일정 편집

Web UI는 촬영, 센서 수집, 유지보수 업무를 폼과 타임라인으로 작성하게 한다. 고급
사용자를 위해 동일한 통합 설정의 JSON 편집과 가져오기·내보내기도 제공한다.

예시 통합 설정은 다음과 같다.

```json
{
  "schema_version": 1,
  "timezone": "Asia/Seoul",
  "policies": {
    "boot-lead-seconds": 120,
    "shutdown-grace-seconds": 60,
    "merge-power-gaps-shorter-than-seconds": 1800
  },
  "activities": [
    {
      "id": "morning-capture",
      "type": "capture",
      "at": "2030-01-01T08:00:00",
      "node": "camera0",
      "profile": "default"
    },
    {
      "id": "temperature-sample",
      "type": "sensor-collection",
      "at": "2030-01-01T10:00:00",
      "node": "environment0",
      "profile": "temperature-humidity"
    },
    {
      "id": "remote-maintenance",
      "type": "maintenance-window",
      "start": "2030-01-01T13:00:00",
      "end": "2030-01-01T15:00:00"
    }
  ]
}
```

### 3.3 계획 미리보기와 적용

설정 변경은 다음 흐름으로 처리한다.

1. 사용자가 Draft 업무 일정을 편집한다.
2. Supervisor가 스키마, 시간대, 노드 capability, 프로필과 일정 충돌을 검증한다.
3. 실행 계획과 전원 계획을 계산한다.
4. Web UI가 원본 업무와 파생 계획을 타임라인으로 비교해 보여 준다.
5. 사용자가 적용하면 새로운 revision을 원자적으로 저장한다.
6. 각 노드 설정과 `pi-power-manager`용 전원 계획을 생성·검증한다.
7. 전체 적용 성공 후에만 revision을 Active로 전환한다.
8. 일부 적용에 실패하면 이전 Active revision을 유지하고 실패 원인을 표시한다.

자동 생성되는 전원 계획은 다음과 같은 형태다.

```json
{
  "source-revision": 17,
  "timezone": "Asia/Seoul",
  "power_schedule": [
    {
      "power-on": "2030-01-01T07:58:00",
      "power-down": "2030-01-01T10:01:00",
      "activities": ["morning-capture", "temperature-sample"],
      "reason": "30분 이하의 작업 간격을 병합"
    },
    {
      "power-on": "2030-01-01T12:58:00",
      "power-down": "2030-01-01T15:01:00",
      "activities": ["remote-maintenance"],
      "reason": "유지보수 구간과 준비·정리 시간"
    }
  ]
}
```

### 3.4 노드별 데이터 조회

Web UI는 로컬 노드를 탐색 가능한 목록으로 제공한다. 각 노드 화면은 다음 공통 정보를
표시한다.

- 노드 ID, 종류, 버전과 capability
- 실행 상태, 마지막 heartbeat와 마지막 오류
- 적용된 설정 및 revision
- 생성 데이터 수, 최근 생성 시각과 사용 저장 공간
- 기간, 데이터 종류, 실행 결과 및 업무 ID 필터
- 데이터 상세, 원본 위치, 생성 시각, 관련 실행과 무결성 정보

노드 유형별 기본 보기는 다음과 같다.

| 노드 유형 | 목록 보기 | 상세 보기 |
|---|---|---|
| CaptureNode | 촬영 시각, 카메라, 파일 크기, 성공 여부, 썸네일 | 이미지 미리보기, 원본 메타데이터, 촬영 설정, 다운로드 |
| Sensor Node | 측정 시각, 센서, 측정값 요약, 품질 상태 | 시계열 그래프, 단위, 원본 레코드, 내보내기 |
| Maintenance | 구간, 서비스 상태, 접속 준비 결과 | 활성화·종료 이력과 관련 진단 이벤트 |
| 향후 로컬 노드 | 공통 데이터 레코드와 노드 제공 요약 | 노드 어댑터가 제공하는 형식별 렌더러 또는 원본 다운로드 |

통합 데이터 화면에서는 여러 노드의 생성 결과를 시간축으로 함께 볼 수 있다. 한 업무
실행에서 생성된 이미지, 센서값과 이벤트는 동일한 `run-id`로 연결한다.

### 3.5 이력과 진단

사용자는 다음 이력을 조회할 수 있다.

- 설정 Draft, 검증, 적용 및 rollback revision
- 계획 계산 결과와 전원 구간 생성 이유
- 노드 준비, 작업 시작·완료·실패 이벤트
- RTC 알람 기록과 read-back 결과
- 종료 실행 또는 가동 유지 결정
- 재부팅 전후 동일 실행을 연결하는 `run-id`

## 4. 시스템 구성

### 4.1 구성 요소

| 구성 요소 | 책임 |
|---|---|
| Web UI | 일정 편집, 계획 미리보기, 상태·데이터·이력 조회 |
| Local API | Web UI에 인증된 설정·계획·노드·데이터 API 제공 |
| Configuration Store | Draft와 Active revision의 원자적 저장 및 rollback |
| Planner | 업무 일정을 실행 계획과 전원 계획으로 변환 |
| Validator | 스키마, capability, 시간, 프로필, 충돌 및 안전 조건 검증 |
| Executor | 계산된 시각에 노드 작업을 조정하고 결과 기록 |
| Node Registry | 로컬 노드 ID, 종류, capability와 어댑터 등록 |
| Data Catalog | 노드 데이터 메타데이터와 업무·실행 관계 색인 |
| Event Store | 상태 전이, 실행 결과, 오류와 감사 이력 저장 |
| Component Adapters | CaptureNode, 센서 및 pi-power-manager 경계 연동 |

### 4.2 로컬 노드 계약

새로운 로컬 노드는 공통 어댑터 계약을 구현해 추가한다.

```python
class ManagedNodeAdapter:
    def capabilities(self): ...
    def validate_activity(self, activity): ...
    def estimate_runtime(self, activity): ...
    def apply_config(self, revision, config): ...
    def prepare(self, run): ...
    def execute(self, run): ...
    def prepare_shutdown(self, deadline): ...
    def health(self): ...
    def list_data(self, query): ...
    def get_data(self, data_id): ...
```

어댑터는 임의 셸 문자열을 실행하지 않는다. 실행할 프로그램과 매개변수는 설치 시
등록된 구현과 검증된 설정으로 제한한다.

### 4.3 데이터 카탈로그 모델

Supervisor는 원본 대신 다음 공통 메타데이터를 저장한다.

| 필드 | 설명 |
|---|---|
| `data-id` | 장치 안에서 고유한 데이터 식별자 |
| `node-id` | 데이터를 생성한 로컬 노드 |
| `activity-id` | 원인이 된 업무 일정 |
| `run-id` | 실제 실행 회차 식별자 |
| `kind` | image, sensor-reading, file, event 등의 유형 |
| `captured-at` | UTC 생성 시각 |
| `uri` | 노드가 관리하는 로컬 원본 위치 또는 조회 핸들 |
| `media-type` | 데이터 표현 형식 |
| `size` | 알려진 경우 원본 크기 |
| `integrity` | 선택 checksum 또는 무결성 상태 |
| `summary` | 목록 화면을 위한 제한된 요약 |

Data Catalog와 실제 원본이 불일치하면 원본을 자동 삭제하지 않고 `missing`,
`unindexed` 또는 `unavailable` 상태로 표시하고 재색인을 제공한다.

### 4.4 저장소

초기 버전은 다음 저장 경계를 사용한다.

```text
/etc/pi-node-supervisor/config.json       Active 업무 설정
/var/lib/pi-node-supervisor/state.db      revision, 계획, 실행, 이벤트, 데이터 색인
/var/lib/pi-node-supervisor/revisions/    적용 가능한 설정 revision
/var/lib/capture-node/...                 CaptureNode 원본 데이터
/var/lib/<sensor-node>/...                센서 노드 원본 데이터
```

설정 JSON은 사람이 검토할 수 있게 유지하고, 관계형 조회가 필요한 계획·이벤트·데이터
카탈로그는 초기에는 SQLite를 사용한다. 모든 내부 시각은 UTC로 저장하고 입력·화면
표시에만 IANA 시간대를 적용한다.

## 5. 계획 및 실행 정책

### 5.1 전원 구간 계산

Planner는 각 업무에 다음 시간을 적용한다.

- 노드별 부팅 후 준비 시간
- 업무 시작 전 준비 시간
- 업무 예상 또는 명시된 실행 시간
- 작업 완료와 데이터 flush 확인 시간
- 안전 종료 여유 시간

겹치는 구간과 정책보다 짧은 간격의 구간은 하나로 병합한다. 병합 결과에는 포함된
업무와 적용 정책을 기록한다. 계산된 전원 계획만 `pi-power-manager`의 선언형 JSON
입력으로 전달한다.

### 5.2 종료 조정

`power-down` 도달 시 다음 순서를 따른다.

1. 새 작업 시작을 막고 관련 노드에 종료 준비를 요청한다.
2. 모든 필수 노드의 작업 완료와 데이터 flush를 확인한다.
3. 다음 `power-on`이 존재하는지 확인한다.
4. `pi-power-manager`가 RTC 알람을 기록하고 read-back 검증한다.
5. 검증된 경우에만 정상 종료를 요청한다.
6. 어느 단계든 실패하면 가동을 유지하고 원인을 기록한다.

### 5.3 재시작 복구

Supervisor는 기동 시 Active revision, 파생 계획, 실제 시각, 노드 상태 및 RTC 상태를
대조한다. 놓친 업무는 활동 유형별 정책에 따라 건너뛰거나 실패로 기록하며, 임의로
중복 실행하지 않는다.

## 6. Web 및 보안

### 6.1 접근 범위

Web UI는 기본적으로 장치의 신뢰된 로컬 유선망에서만 제공한다. 인터넷 공개를
전제로 하지 않는다. 초기 버전부터 로그인, 세션 만료, CSRF 방어와 변경 감사 기록을
제공한다.

### 6.2 권한

| 역할 | 권한 |
|---|---|
| Viewer | 상태, 계획, 노드 데이터와 이력 조회 |
| Operator | Draft 일정 작성, 검증 및 적용 요청 |
| Administrator | 노드·프로필·보존 정책 및 사용자 관리 |

Web 프로세스는 RTC 쓰기나 시스템 종료 권한을 갖지 않는다. 실제 전원 변경은
검증된 계획을 받은 `pi-power-manager`의 제한된 권한 경로만 수행한다.

### 6.3 데이터 제공 안전성

- 파일 경로를 사용자 입력으로 직접 조합하지 않는다.
- 데이터 조회는 `data-id`와 노드 어댑터를 통해 허용된 원본만 제공한다.
- 이미지 미리보기와 다운로드에 크기 및 처리 시간 제한을 둔다.
- 센서 내보내기는 기간과 행 수 제한을 둔다.
- 비밀번호, 토큰 및 개인 인증정보를 설정·로그·데이터 카탈로그에 평문 저장하지 않는다.
- 원본 삭제는 조회와 분리된 명시적 권한 및 확인 절차로만 제공한다.

## 7. 개발 범위

### 7.1 초기 포함 범위

- 단일 Raspberry Pi 내부 실행
- CaptureNode, 하나 이상의 센서 노드 및 pi-power-manager 어댑터
- 일회성 촬영, 센서 수집과 유지보수 구간
- 통합 JSON 설정, Web 폼 편집과 JSON 가져오기·내보내기
- 설정 검증, 실행·전원 계획 생성과 적용 미리보기
- revision 기반 원자적 적용과 이전 설정 유지
- 대시보드, 노드 목록, 노드별 데이터 조회
- 이미지 썸네일·상세 보기와 센서 시계열 그래프
- 실행·전원·RTC·오류 이력 조회
- systemd 기반 자동 시작과 로컬 인증

### 7.2 제외 범위

- 여러 Raspberry Pi를 중앙에서 통합 관제하는 기능
- 장치가 꺼져 있을 때 Web UI 접속 보장
- 인터넷 기반 SaaS, Cloud 동기화 및 외부 알림
- CaptureNode 촬영 및 센서 드라이버 자체 재구현
- pi-power-manager의 RTC 및 종료 로직 재구현
- 원본 데이터의 자동 이동·변환·삭제
- 모바일 전용 앱
- 임의 사용자 스크립트 실행

## 8. 단계별 계획

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 0. 계약 검증 | CaptureNode, pi-power-manager, 센서 노드의 설정·상태·데이터 경계 확인 | 어댑터 계약과 샘플 데이터로 end-to-end 계획 검증 |
| 1. Planner MVP | 업무 JSON, 검증, 실행·전원 계획과 dry-run | 대표 업무에서 결정적인 전원 계획 생성 |
| 2. Local Executor | revision 적용, 노드 준비·실행·완료, 안전 종료 조정 | 가짜 노드로 재시작 포함 전체 실행 주기 통과 |
| 3. Web Control | 대시보드, 일정 편집, 계획 비교와 적용 | Web에서 Draft부터 Active revision까지 완료 |
| 4. Data Explorer | 노드별 데이터 카탈로그, 이미지와 센서 조회 | run-id로 다중 노드 결과를 통합 조회 |
| 5. 안정화 | 인증, 권한, 감사, 복구, 저장 한계와 HIL | Pi 5에서 반복 업무·종료·기동 및 데이터 완결성 검증 |
| 6. 노드 확장 | 플러그인 등록과 새 로컬 노드 어댑터 | 기존 Core 변경 없이 샘플 노드 추가 |

## 9. 주요 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 촬영·수집 중 종료 | 데이터 손상 또는 누락 | 노드별 `prepare_shutdown`과 완료 확인 실패 시 가동 유지 |
| 잘못된 전원 계획 | 다음 업무 미실행 | 업무와 파생 계획 비교, 다음 power-on 필수, RTC read-back |
| 설정 일부 적용 | 노드 간 불일치 | revision 단위 검증·원자적 적용과 rollback |
| 원본과 색인 불일치 | 데이터 조회 오류 | 상태 표시, 재색인 및 원본 비파괴 정책 |
| 대용량 이미지 조회 | Web 응답 지연·메모리 사용 | 썸네일 캐시, streaming, pagination과 크기 제한 |
| 센서 데이터 장기 증가 | 저장 공간 고갈 | 노드별 보존 정책, 용량 경고와 제한된 집계 |
| Web 권한 확대 | RTC·종료 오용 | Web과 특권 실행 경로 분리, 역할 기반 권한과 감사 |
| 장치 종료 중 Web 단절 | 설정 변경 중단 | 적용 전 경고, 유지보수 구간과 원자적 Draft 저장 |
| 새 노드 계약 불일치 | Supervisor 복잡도 증가 | capability와 버전이 있는 공통 어댑터 계약 |

## 10. 초기 완료 조건

- 사용자가 Web에서 촬영, 센서 수집 및 유지보수 업무를 작성할 수 있다.
- 업무에서 자동 생성된 실행 계획과 전원 계획을 적용 전에 확인할 수 있다.
- 전원 구간마다 생성 원인과 관련 업무를 추적할 수 있다.
- CaptureNode 이미지와 센서 측정값을 노드별·기간별로 조회할 수 있다.
- 동일 실행의 여러 노드 데이터가 `run-id`로 연결된다.
- 설정 또는 노드 적용 실패 시 이전 Active revision이 유지된다.
- 작업 완료, 다음 기동 및 RTC 검증 없이는 자동 종료하지 않는다.
- 장치 재시작 후 Active revision과 실행 상태가 일관되게 복구된다.
- Web 프로세스는 RTC 쓰기와 시스템 종료 권한을 직접 갖지 않는다.
- 실제 Pi 5에서 대표 업무의 촬영·수집·종료·RTC 기동·데이터 조회 주기를 반복 검증한다.
